# Research Humanizer 2.3.3

**Preview release.** Research reasoning and gap validation extend the existing research-paper-craft skill. The full-paper and ARS workflow introduced in 2.3.0 remains in place.

## Added and extended

- Add English and Thai research-reasoning guidance for gap validity, originality, scoped impact, RQ-method-evidence alignment, findings and limitations. Link existing modules instead of rebuilding their content.
- Distinguish Practical Problem, Research Gap and Proposed Solution. Separate supported gap existence from evidence-based gap closure. An empty search is not proof of universal novelty.
- Keep scientific, methodological and practical impact separate from whether it is expected or demonstrated. Preserve replication, confirmation, negative results, qualitative inquiry and theoretical work without a mandatory numeric baseline.
- Add feedback classification and validation within the existing Decision log. One expert's advice does not automatically become a universal rule. Persist only approved, appropriately scoped and de-identified principles in version-controlled files.
- Add the required scientific-audit table and six summaries to existing QA guidance. Use six support statuses separately from execution states and evidence classes. Do not invent research-quality scores.
- Route scientific audits, substantive revisions and full-paper stages through the new module. Language-only humanizing stays lightweight. Scientific changes require researcher approval.
- Extend audit_full_paper.py with an optional reasoning_review member. Existing schema-1 inputs without that member keep their prior output shape and behavior. Reuse record locators. No CSV header migration, new skill, second ARS pipeline or new CLI is introduced.

## Preserved

Original Humanizer text and all existing R00–R47 rule bodies remain unchanged. The four other audit scripts, Word guidance, punctuation handling, equations, figure requirements, mandatory missing-source questions and upstream notices remain. ARS retains ownership of workflow state and confirmation points. This is prompt-level coordination, not enforced inter-agent execution.

## Verification and limitations

Executed software checks are recorded in ../verification/release-v2.3.3.json and ../VERIFICATION.md. Authored synthetic tests assess record consistency and static instructions, not source truth, originality, method validity or improved model prose. Live Claude/Codex/ARS integration, independent model evaluation and native Word rendering or repair were not run. References in a JSON record can be wrong; the checker does not open them or approve publication.
