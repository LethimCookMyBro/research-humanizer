# ผลตรวจ Research Paper Craft v2.0

ตรวจวันที่ 15 พฤศจิกายน 2026 จากไฟล์ `research-paper-craft-v2.0.zip` ที่อยู่ในบทสนทนานี้ ไม่ได้อาศัยคำตอบเดิมเป็นหลักฐานแทนไฟล์

## ข้อสรุป

กฎที่ผู้ใช้ระบุมีอยู่ในระดับคำสั่ง รวมถึง Humanizer สำหรับงานวิจัย สมการ การถามผู้วิจัยก่อนเติมข้อมูลที่ขาด การตรวจข้อมูลดิบ ฉบับ anonymous และการตรวจทุกหน้าจาก Word จริง

ยังไม่ควรเรียกว่าปิดทุกช่องโหว่หรือทดสอบการทำงานครบแล้ว พบจุดที่ตัวตรวจข้อความพลาดจริง และยังไม่มีผลทดสอบพฤติกรรมโมเดลหรือการใช้งานทั้งกระบวนการในระบบเป้าหมาย

สถานะที่เหมาะสมจากหลักฐานรอบนี้คือชุดคำสั่งสำหรับทดลองใช้งาน พร้อมข้อจำกัดที่เปิดเผย ไม่ใช่การรับรองผลการเขียนบทความโดยอัตโนมัติ การเผยแพร่สาธารณะยังต้องยืนยันสิทธิของเนื้อหาที่นำมารวมและกำหนดสิทธิใช้แพ็กเกจให้ชัด

รอบนี้เป็นการตรวจและจัดทำหลักฐาน ไม่ได้แก้ไฟล์ต้นฉบับ ไม่ได้สร้าง v2.1 ไม่ได้ติดตั้งในระบบของผู้ใช้ และไม่ได้อัปโหลด GitHub

## ขอบเขตและวิธีตรวจ

เปิด ZIP และอ่าน SKILL.md, README, คู่มือภาษาอังกฤษทั้งแปดหมวด, ส่วนภาษาไทยของกฎสำนวน สมการ บทนำ Contributions และการตรวจก่อนส่ง, สคริปต์ตรวจข้อความ, ชุดทดสอบ, แบบบันทึก และรายงานตรวจเดิม

เทียบกับข้อกำหนดในบทสนทนา ตรวจโครงสร้างทั้งสองภาษาและรหัสกฎด้วยชุดทดสอบเดิม ตรวจค่า SHA256 ที่แนบ รันชุดทดสอบเดิมใหม่ แล้วทดลองกรณีขอบเขตด้วยข้อความสมมติ การทดสอบสองภาษาด้วยรหัสกฎเป็นการตรวจโครงสร้าง ไม่ใช่การพิสูจน์ว่าคำแปลทุกบรรทัดมีความหมายเท่ากัน

ไม่ได้ทดลองกับโมเดลอิสระ ไม่ได้สร้าง paper จริง ไม่ได้ตรวจ Word หรือไฟล์ anonymous จริง ไม่ได้ทำการทดสอบความปลอดภัยครบทุกชนิด และไม่ได้พิสูจน์ความถูกต้องทางวิทยาศาสตร์ของงานวิจัยใด

## ช่องว่างที่พบและวิธีปิด

### G01 คำย่อภาษาอังกฤษบางคำไม่ถูกตรวจพบ

สถานะเป็นข้อบกพร่องที่ทำซ้ำได้

ข้อความทดสอบ `Here's the result.` คืนรายการว่าง ทั้งที่ R07 ห้าม contractions สาเหตุอยู่ที่รายการคำใน regular expression ของ `scripts/lint_manuscript.py` บรรทัด 18 ถึง 21 ซึ่งไม่มี `here`

แก้รายการ contraction ที่ชัดเจน เพิ่มกรณีทดสอบ apostrophe ทั้งแบบตรงและโค้ง และรักษา possessive เช่น `the author's method` ไม่ให้กลายเป็นการแก้ผิด ห้ามใช้การแทนคำอัตโนมัติโดยไม่แยกบริบทที่กำกวม

### G02 เครื่องหมายรอข้อมูลถูกซ่อนจากตัวตรวจได้ด้วยรูปแบบข้อความ

สถานะเป็นข้อบกพร่องที่ทำซ้ำได้

ทั้ง `Result $[RESULT UNVERIFIED]$.` และ ``Result `[RESULT UNVERIFIED]`.`` คืนรายการว่าง ข้อความใน math และ inline code ถูกลบออกจากข้อความชั่วคราวก่อนค้น draft marker ในสคริปต์บรรทัด 100 ถึง 102

แยกการตรวจสถานะร่างออกจากการตรวจเครื่องหมายสำนวน ค้น draft marker ในตำแหน่งที่เกี่ยวข้องก่อนปิดบัง syntax แล้วรายงานให้ทบทวนโดยไม่แก้สมการหรือโค้ดเอง กรณีที่บทความกำลังอธิบาย marker อย่างตั้งใจต้องมีการทบทวน ไม่ใช่ลบ marker เงียบ ๆ

### G03 ส่วนที่ยกเว้นการตรวจเปิดแล้วไม่ปิดอาจทำให้ผลเป็น "ไม่พบปัญหา"

สถานะเป็นข้อบกพร่องที่ทำซ้ำได้

ทดสอบบรรทัดเปิด YAML `---` โดยไม่มีบรรทัดปิด และบรรทัดเปิดสมการ `$$` โดยไม่มีบรรทัดปิด พบว่าข้อความด้านหลังที่มี contraction และ semicolon ถูกข้ามโดยไม่มีคำเตือน สาเหตุอยู่ที่การคงสถานะ `in_yaml` หรือ `display_end` จนจบไฟล์ โดยไม่มีการตรวจสถานะที่ยังเปิดค้างก่อนคืนผล

เพิ่มการรายงานส่วน syntax ที่ไม่ปิด พร้อมตำแหน่งเริ่มต้น และระบุว่าการตรวจช่วงนั้นไม่สมบูรณ์ ห้ามสรุปว่าข้อความสะอาดจากผลที่ข้ามช่วงเนื้อหาไป

### G04 กฎครบกว่าขอบเขตตัวตรวจอัตโนมัติ

สถานะเป็นขอบเขตที่เอกสารเปิดเผยอยู่แล้ว ไม่ควรเรียกทั้งหมดว่าบั๊ก

ตัวตรวจปัจจุบันไม่มีการตรวจบริบท Greek symbols หรือตัวเลขใน Contributions การทดลอง `The parameter α was held fixed.` และหัวข้อ Contributions ที่มี `12%` จึงไม่พบข้อสังเกต แม้มีคำสั่งห้ามอยู่ในคู่มือ

README บรรทัด 61 ถึง 63 ระบุว่าเครื่องมือเป็น heuristic และไม่ตรวจความหมายสัญลักษณ์ วิทยาศาสตร์ การปกปิดชื่อหรือหน้ากระดาษ การตรวจด้วยคนหรือโมเดลยังเป็นข้อบังคับตามคู่มือ

เพิ่มการตรวจแบบเตือนเฉพาะที่ทำได้อย่างปลอดภัย หรือทำ checklist แบบใช้หลักฐานจริงให้เป็นเงื่อนไขส่งมอบ อย่าอ้างว่าการเพิ่ม regular expression ทำให้ตรวจความหมายหรือสูตรได้ครบ กฎเกี่ยวกับหลายย่อหน้า ความเป็นธรรมชาติ ความถูกต้องของสูตร และความหมายของสัญลักษณ์ยังต้องอาศัยบริบท

### G05 ยังไม่ทดสอบพฤติกรรมโมเดลและการใช้งานทั้งกระบวนการ

สถานะเป็นหลักฐานที่ยังขาด ไม่ใช่ข้อพิสูจน์ว่าโมเดลทำไม่ได้

`tests/acceptance-scenarios.md` บรรทัด 3 ถึง 7 และ `tests/verification-report.md` บรรทัด 23 ถึง 27 ระบุว่าโจทย์พฤติกรรม 40 สถานการณ์และการติดตั้งในระบบผู้ใช้ยังไม่ได้ทดสอบ

ก่อนกล่าวว่าใช้งานได้ครบในระบบใด ต้องรันกับโมเดลและระบบนั้นจริง บันทึกเวอร์ชัน คำสั่ง ไฟล์นำเข้า ผลลัพธ์ และการเปิดอ่านคู่มือ ทดสอบหลายรอบในบริบทใหม่โดยไม่อาศัยประวัติแชตเดิม ถ้าจะกล่าวว่า skill ช่วยให้ดีขึ้น ต้องมีการเปรียบเทียบกับงานเดียวกันที่ไม่ใช้ skill

เพิ่มตัวอย่างข้อความวิจัยทั้งไทยและอังกฤษสำหรับตรวจสำนวน พร้อมรายการความหมายที่ต้องคงเดิม เช่น ตัวเลข หน่วย คำปฏิเสธ เงื่อนไข ขอบเขต และระดับความแน่ใจ ประเมินความเป็นธรรมชาติด้วยเกณฑ์ที่อธิบายได้และผู้ทบทวน ไม่ใช้คะแนน AI detector เป็นหลักฐานคุณภาพ

สำหรับคำกล่าวว่ารองรับ full paper ให้ทดสอบด้วยชุดงานตัวอย่างที่มีสมการ โค้ด ผล กราฟ และภาพจริง แล้วตรวจการเชื่อมข้อมูลข้ามส่วน การเกลาภาษาไม่ควรทำให้คำว่า "may" หายไปหรือขยายผลเกินข้อมูล สำหรับ workflow Word และ anonymous ต้องเก็บหลักฐานการตรวจไฟล์จริงด้วย การใช้ชุดข้อมูลสังเคราะห์เพื่อทดสอบกระบวนการทำได้หากติดป้ายชัดและไม่อ้างว่าเป็นผลวิจัยจริง

### G06 เกณฑ์กฎบังคับกับข้อเตือนด้านสำนวนควรชัดขึ้น

สถานะเป็นข้อเสนอปรับความชัด ไม่ใช่ความผิดพลาดที่พิสูจน์พฤติกรรมแล้ว

R07 ใช้คำว่าห้าม แต่ R28 บรรทัด 66 อนุญาตให้สำนวนเล็กน้อยเป็น warning ยังไม่ได้ยกตัวอย่างว่าการละเมิดเครื่องหมายที่ผู้ใช้ห้ามอยู่กลุ่มใด

ควรระบุว่าข้อห้ามชัดของผู้ใช้ เช่น contractions เครื่องหมายต้องห้าม และตัวเลขผลใน Contributions เป็นรายการที่ต้องแก้ก่อนระบุว่าผ่าน house style ส่วนเรื่องจังหวะประโยคหรือความยาวย่อหน้าที่ไม่กระทบความหมายเป็นข้อเสนอแนะ ข้อกำหนดวารสารที่ขัดกับ house style ต้องบันทึกเหตุผลตาม R00 ไม่ละเมิดเงียบ ๆ

### G07 สิทธิการเผยแพร่ยังไม่ครบในระดับแพ็กเกจ

สถานะเป็นเรื่องที่ต้องยืนยันก่อนเผยแพร่ต่อในฐานะชุดที่ผู้อื่นนำไปใช้ได้

ZIP ไม่มีไฟล์ LICENSE ของแพ็กเกจ และ SKILL.md ไม่มีช่อง license Humanizer ที่เก็บใน provenance มี `license: MIT` แต่ในแพ็กเกจนี้ไม่พบข้อความ license ฉบับเต็มและ copyright notice ของต้นทาง มีที่มาว่าเป็นไฟล์ที่ผู้ใช้ส่งมาและอ้างถึง Wikipedia ในเนื้อหา ซึ่งยังไม่ทำให้ระบุเจ้าของสิทธิของไฟล์ทั้งฉบับได้

การไม่มี LICENSE ไม่ทำให้รูปแบบ Agent Skills ผิด เพราะช่องนี้เป็น optional แต่ควรเลือกสิทธิใช้ส่วนที่สร้างขึ้นใหม่ และยืนยันแหล่งต้นทาง เจ้าของสิทธิ เวอร์ชัน และข้อความสิทธิของส่วนที่นำมารวมก่อนแจกสาธารณะ ไม่ควรเดาชื่อเจ้าของสิทธิหรือถือว่าป้าย MIT ในไฟล์หนึ่งครอบคลุมทั้งแพ็กเกจ

เพิ่ม LICENSE ตามสิทธิที่เจ้าของเลือก และบันทึก third-party notices เมื่อยืนยันต้นทางแล้ว การอัปโหลด GitHub แบบ public กับการให้สิทธิใช้ซ้ำแบบ open source เป็นคนละเรื่อง

## การปรับเพื่อดูแลบน GitHub

ข้อเสนอด้านการดูแลต่อไปนี้ไม่ใช่เงื่อนไขบังคับของ Agent Skills และไม่จำเป็นต้องใส่เพิ่มในคำสั่งหลักที่โมเดลโหลดทุกครั้ง

- เพิ่มกระบวนการรัน tests เมื่อมีการเปลี่ยนไฟล์ เพื่อป้องกันข้อผิดพลาดเดิมกลับมา พร้อมเพิ่มห้ากรณีที่พบรอบนี้หลังแก้สคริปต์
- เพิ่ม `.gitignore` เพื่อไม่ติดข้อมูลดิบส่วนตัว รหัสลับ ไฟล์ผลทดลองจริง และ cache โดยไม่ตั้งใจ รายการป้องกันต้องเหมาะกับโครงสร้าง repository ที่เลือกจริง
- เพิ่มบันทึกการเปลี่ยนแปลงและรายการระบบที่ทดสอบจริง ไม่ใช้คำว่าใช้ได้กับทุก AI โดยไม่มีหลักฐาน
- แยกสถานะ package tests, behavior tests และ manuscript checks ใน README ให้เห็นต่างกัน
- เพิ่มตารางตรวจสองภาษาจากคู่ข้อความและตัวอย่างผลลัพธ์ การเทียบรหัสหัวข้ออย่างเดียวไม่ตรวจความหมายที่แปลคลาดเคลื่อน

ไม่จำเป็นต้องขยาย SKILL.md เป็นคู่มือยาวอีก หลักฐานการรัน ชุดทดสอบ และข้อมูลสิทธิควรอยู่ในไฟล์ประกอบ
